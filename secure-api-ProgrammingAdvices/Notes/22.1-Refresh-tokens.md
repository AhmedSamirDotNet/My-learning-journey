# 📖 Token Lifecycle: Expiration & Refresh Tokens

### 🗝️ Introduction

At this stage, your API correctly authenticates users and enforces permissions. However, in production, security is not a one-time event—it is a **lifecycle**. Since JWTs are stateless (the server doesn't store sessions), once a token is issued, it remains valid until it expires. This creates a significant security challenge that must be managed.

---

### ❓ Why JWTs Must Expire

Every JWT includes an `exp` (expiration) claim. This is mandatory in professional systems for several reasons:

1. **Token Theft:** Tokens can be stolen from browser storage (XSS), local logs, or memory.
2. **Revocation Limitations:** You cannot easily "kill" a JWT because the server doesn't track it.
3. **Damage Control:** Expiration doesn't prevent theft, but it limits the "useful life" of a stolen token.

---

### ⚠️ The Core Tradeoff: Security vs. Usability

- **Long-Lived Tokens:** Dangerous. If stolen, an attacker has permanent access without needing a password.
- **Short-Lived Tokens:** Secure, but ruin the User Experience (UX) because the user must log in every 5 minutes.

**The Solution:** The **Refresh Token** strategy.

---

### 🧩 The Concept of Refresh Tokens

The idea is to use two distinct types of tokens:

1. **Access Token:**
   - Short lifespan (e.g., 15 minutes).
   - Sent with every API request.
   - Purpose: "Permission to perform an action."
2. **Refresh Token:**
   - Long lifespan (e.g., 7 days).
   - Never used to access business data directly.
   - Purpose: "Permission to request a new Access Token."

---

### 🚫 The Golden Rule: No Direct API Access

A Refresh Token has exactly ONE job. It should never be used for business endpoints such as:

- `GET /students` ❌
- `DELETE /orders/5` ❌
  A Refresh Token is only sent to a single, dedicated endpoint: `POST /auth/refresh`.

---

### 🔁 Refresh Token Rotation

This is a high-security pattern where every time a Refresh Token is used to get a new Access Token:

1. The server issues a **new** Access Token.
2. The server issues a **new** Refresh Token.
3. The **old** Refresh Token is invalidated/deleted.
   **Why?** If a thief steals a Refresh Token and uses it, and then the real user tries to use their (now old) token, the server detects the reuse and kills the entire session, neutralizing the attack.

---

### 🚪 How Logout Works in Stateless APIs

In traditional session-based systems, we delete the session from the database. In JWT:

- The server cannot "delete" the Access Token (it's in the user's hands).
- **Logout means:** Deleting or revoking the Refresh Token from the server's database.
- **Result:** Once the current Access Token expires naturally (in a few minutes), the client cannot renew it, and the user is effectively logged out.

---

### 🔁 The Renewal Flow (Step-by-Step)

1. **Token Expires:** Client calls the API with an expired Access Token ➡️ Server returns `401 Unauthorized`.
2. **Silent Renewal:** The client sends the Refresh Token to `/auth/refresh`.
3. **Server Validation:** The server checks: Is the token known? Not expired? Not revoked? Not reused?
4. **Issue New Pair:** If valid, the server returns a brand-new pair (Access + Refresh).
5. **Continuity:** The client replaces the old tokens and continues working. The user never sees a login screen.

---

### 🏁 Mental Model Summary

📌 **Access Token:** The key that opens the doors to do work.
📌 **Refresh Token:** The receipt used to ask for a new key.

**You are no longer building a demo; you are building a system that knows how to survive, recover, and limit damage in the real world.**

# 📖 دورة حياة التوكن: Expiration & Refresh Tokens

### 🗝️ مقدمة (Introduction)

حتى الآن، الـ API الخاص بك يقوم بعملية الـ Authentication بنجاح. ولكن في الأنظمة الحقيقية، الأمان ليس مجرد "حدث" يقع مرة واحدة عند الـ Login، بل هو **دورة حياة (Lifecycle)**.
بما أن الـ JWT عبارة عن "Stateless Token" (السيرفر لا يخزن جلسات)، فهذا يعني أن التوكن بمجرد صدوره يظل صالحاً حتى تنتهي مدته، وهنا تظهر المشاكل الأمنية.

---

### ❓ لماذا يجب أن تنتهي صلاحية التوكن (Expiration)؟

الـ JWT يحتوي على الـ `exp` claim، وهو ليس اختيارياً في الأنظمة القوية.
**الأسباب:**

1. **سرقة التوكن:** التوكن قد يُسرق من المتصفح، الـ Logs، أو الـ Memory.
2. **عدم إمكانية الإلغاء:** لا يمكنك "سحب" التوكن من يد المستخدم بسهولة لأنه Stateless.
3. **تقليل الأضرار:** انتهاء الصلاحية لا يمنع السرقة، ولكنه يحدد "عمر" التوكن المسروق، مما يجعل الضرر محدوداً بمدة زمنية قصيرة.

---

### ⚠️ المعضلة: الأمان vs سهولة الاستخدام

- **التوكن طويل الأمد (Long-lived):** خطر جداً. لو سُرق، المهاجم يملك صلاحيات دائمة دون الحاجة لباسورد.
- **التوكن قصير الأمد (Short-lived):** أمان عالي، ولكن تجربة مستخدم سيئة (المستخدم سيضطر لعمل Login كل 5 دقائق).

**الحل:** استخدام نظام الـ **Refresh Tokens**.

---

### 🧩 مفهوم الـ Refresh Tokens

الفكرة بسيطة: نستخدم نوعين من التوكنز:

1. **Access Token:**
   - عمر قصير جداً (دقائق).
   - يُرسل مع كل طلب للـ API.
   - وظيفته: "السماح بالقيام بفعل معين".
2. **Refresh Token:**
   - عمر طويل (أيام/أسابيع).
   - لا يُستخدم للوصول للبيانات أبداً.
   - وظيفته الوحيدة: "طلب Access Token جديد".

---

### 🚫 القاعدة الذهبية: لا تستخدم الـ Refresh Token للوصول للبيانات

يمنع تماماً إرسال الـ Refresh Token في طلبات مثل:

- `GET /students` ❌
- `DELETE /courses/5` ❌
  الـ Refresh Token وظيفته الوحيدة هي الذهاب لنقطة نهاية واحدة فقط وهي الـ `POST /auth/refresh` للحصول على مفاتيح جديدة.

---

### 🔁 تدوير التوكن (Refresh Token Rotation)

تعني أنه في كل مرة تستخدم فيها الـ Refresh Token للحصول على Access Token جديد، يقوم السيرفر بـ:

1. إصدار Access Token جديد.
2. إصدار Refresh Token **جديد** تماماً.
3. إلغاء (Invalidate) الـ Refresh Token القديم.
   **الفائدة:** إذا سُرق الـ Refresh Token واستخدمه المخترق، ثم حاول المستخدم الحقيقي استخدامه، سيكتشف السيرفر أن التوكن استُخدم مرتين ويلغي الجلسة بالكامل، مما يكشف عملية السرقة.

---

### 🚪 كيف يعمل الـ Logout في الأنظمة Stateless؟

في الأنظمة القديمة (Sessions)، كنا نمسح الجلسة من السيرفر. في JWT:

- السيرفر لا يمسح الـ Access Token (لأنه لا يملكه أصلاً).
- **الـ Logout يعني:** مسح أو إلغاء الـ Refresh Token من قاعدة البيانات في السيرفر.
- **النتيجة:** بمجرد انتهاء صلاحية الـ Access Token الحالي (بعد دقائق)، لن يستطيع العميل تجديده، وبذلك تنتهي الجلسة "طبيعياً".

---

### 🔁 رحلة التجديد (The Renewal Flow)

1. **انتهت الصلاحية:** العميل يرسل طلب بـ Access Token منتهي ⬅️ السيرفر يرد بـ `401 Unauthorized`.
2. **طلب التجديد:** العميل يرسل الـ Refresh Token لنقطة الـ `/auth/refresh`.
3. **التحقق:** السيرفر يتأكد: هل التوكن معروف؟ غير منتهي؟ لم يتم إلغاؤه؟ لم يُستخدم من قبل؟
4. **الإصدار:** إذا كان كل شيء سليم، يصدر السيرفر طقم توكنز جديد (Access + Refresh).
5. **الاستمرارية:** العميل يحفظ التوكنز الجديدة ويكمل عمله دون أن يشعر المستخدم بأي انقطاع.

---

### 🏁 الخلاصة (النموذج الذهبي)

📌 **Access Token:** هو المفتاح الذي يفتح الأبواب (لإنجاز العمل).
📌 **Refresh Token:** هو الإيصال الذي يطلب مفتاحاً جديداً (لتجديد الصلاحية).

**أنت الآن لا تبني API "شغال" فقط، أنت تبني نظاماً يعرف كيف يحمي نفسه وكيف يتعافى من المخاطر.**
