### 1. تكوين الـ Refresh Token وشكله في الداتا بيز

الـ Refresh Token غالباً بيكون عبارة عن **Cryptographically Secure Random String** (رقم عشوائي طويل ومعقد)، مش JWT.
**ليه؟** عشان نقدر نتحكم فيه براحتنا (نلغيه أو نعدله) من غير ما نستنى وقته يخلص.

في الداتا بيز، بيكون ليه جدول (مثلاً اسمه `UserRefreshTokens`) وأعمدته كالتالي:

- **Token Hash:** الـ Hash بتاع الرقم العشوائي (عشان لو الداتا بيز اتسربت، التوكنز متبقاش مكشوفة).
- **UserId:** التوكن ده بتاع مين.
- **ExpiresAt:** تاريخ الانتهاء (عشان السيرفر يعرف هو لسه صالح ولا لاء).
- **IsRevoked:** ده Boolean (صح أو غلط) أو تاريخ `RevokedAt`.
- **CreatedByIp / ReplacedByToken:** (اختياري) عشان تتبع الـ Rotation.

**📌 سؤال مهم: نمسحه ولا نعلم عليه Revoked؟**
الأفضل "تقنياً" إنك تعمل له **Revoke** (تخلي الـ Boolean بـ True) أو تسجل تاريخ الـ Revocation.
**ليه؟** عشان لو حصلت محاولة اختراق، تقدر ترجع للـ Logs وتعرف التوكن ده اتلغى امتى ومين اللي استخدمه. لكن في الأنظمة البسيطة، المسح شغال ومفيش مشكلة.

### 2. السيناريو الكامل (اللوجيك من الصفر)

#### أ- مرحلة الـ Login

1.  السيرفر يتأكد من بياناتك (Email/Password).
2.  يكريه **Access Token** (ده JWT، جواه الـ Expire بتاعه، والسيرفر مش بيخزنه).
3.  يكريه **Refresh Token** (رقم عشوائي طويل).
4.  السيرفر يحفظ بيانات التوكن في الداتا بيز: `(UserId, Hash(Token), ExpiresAt, IsRevoked=false)`.
5.  يبعتلك الـ Access والـ Refresh "سليم" (الرقم العشوائي نفسه اللي لسه معملوش هاش).

#### ب- مرحلة الـ Refresh Request

1.  الـ Access Token مات. الكلاينت بيبعت الـ Refresh Token (الرقم العشوائي).
2.  السيرفر ياخد الرقم، يعمل له Hash، ويدور عليه في جدول الـ Refresh Tokens.
3.  **بيعمل 3 اختبارات أساسية:**
    - هل التوكن موجود في الداتا بيز؟
    - هل تاريخ الـ `ExpiresAt` لسه مجاش؟ (لم ينتهِ وقته).
    - هل الـ `IsRevoked` قيمتها `False`؟ (لم يتم إلغاؤه).
4.  **لو كله تمام (Valid):**
    - يعلم على التوكن القديم إنه **Revoked** (أو يمسحه).
    - يعمل واحد جديد خالص ويسجله في الداتا بيز (**Rotation**).
    - يبعتلك الـ Access والـ Refresh الجداد في الـ Response.

#### ج- مرحلة الـ Logout

1.  السيرفر يستلم الـ Refresh Token من الكلاينت.
2.  يدور عليه بالـ Hash، ويقوم عامله **Revoke** فوراً أو يمسحه من الجدول.
3.  **بالنسبة للـ Access Token:** زي ما اتفقنا، هو لسه شغال في جيب الكلاينت (عشان هو JWT والسيرفر مش بيتشيك عليه في الداتا بيز في كل Request).
4.  **النتيجة:** اليوزر هيفضل "صوريّاً" عامل Login لمدة دقيقتين (عمر الـ Access Token متبقي فيه)، لكن بمجرد ما يحاول يجدد (Refresh)، السيرفر هيقوله "أنت مين؟ التوكن بتاعك ملغي في الداتا بيز عندي"، فيقوم السيستم طارده للـ Login Page.

### 💡 ملخص الفرق النهائي (عشان متتلخبطش)

- **Access Token:** زي "تذكرة المترو"، السيرفر بيبص عليها يتأكد من ختمها (الـ Signature) وخلاص، مش بيسأل الداتا بيز (**Stateless**).
- **Refresh Token:** زي "كارت الاشتراك"، السيرفر لازم يفتح الدفتر (الداتا بيز) يتأكد إن الكارت ده لسه ساري ومش مسروق أو ملغي (**Stateful**).

## 🧐 1. The Core Philosophy (The "Why")

Stateless authentication (JWT) faces a dilemma:

1.  **Short-lived Access Tokens:** Great for security (if stolen, they expire fast), but terrible for UX (user logs out every 15 mins).
2.  **Long-lived Access Tokens:** Great for UX, but a disaster for security (if stolen, the hacker has access for days).

**The Solution:** Use two tokens.

- **Access Token:** Your "Temp Key" (Fast, short-lived, carried in every request).
- **Refresh Token:** Your "Master Key" (Used only to get a new Temp Key, stored securely).

## 🔄 2. The Full Life-Cycle (Step-by-Step Logic)

### A. The Login Phase

1.  User sends credentials (Email/Password).
2.  Server validates and generates:
    - **Access Token:** (e.g., expires in 15 mins).
    - **Refresh Token:** (A secure random Base64 string).
3.  Server **Hashes** the Refresh Token and saves it in the Database (with an expiry date).
4.  Server sends both to the Client.

### B. The Refresh Phase (The "Magic" part)

1.  Access Token expires ➔ Client sends the **Refresh Token + Email** to `/refresh`.
2.  Server hashes the received token and compares it with the stored Hash.
3.  **Validation Check:**
    - Does the Hash match?
    - Is it expired?
    - Is it **Revoked**? (Has it been cancelled manually?)
4.  If valid, the Server performs **Rotation**:
    - **Deletes/Revokes** the old Refresh Token.
    - Generates a **NEW** Access Token.
    - Generates a **NEW** Refresh Token (and stores its Hash).
5.  Client receives the new pair and continues working seamlessly.

### C. The Logout Phase

1.  Client calls `/logout` sending the Refresh Token.
2.  Server finds the Hash and **Revokes** it (Sets `RevokedAt = Now`).
3.  Even if the Client still has the string, it’s now useless because the Server’s "Source of Truth" says it's dead.

## 🛡️ 3. Security Deep-Dive (Your Smart Questions)

### Q: What if the Access Token is still valid after Logout?

This is the "Zombie Token" problem. Since JWT is stateless, the server doesn't check the DB for every request.

- **The Industry Solution:** Keep Access Token life very short (e.g., 5 minutes). Even if a user logs out, the stolen token only works for those remaining 5 minutes.
- **Pro Solution:** Use a "Blacklist" in a fast cache like Redis, but usually, short expiry is enough for 99% of apps.

### Q: Why do we use Hashing for Refresh Tokens?

Because if your Database is leaked, the hacker will find the Hashes, not the actual tokens. They cannot use a Hash to log into your API. It's the same reason we hash passwords!

### Q: What is "Rotation" and why is it cool?

Rotation means every time you use a Refresh Token, it dies and a new one is born.

- **Benefit:** If a hacker steals your Refresh Token and uses it, **YOU** will be logged out the next time your app tries to refresh (because the token was already used). This acts as a "Breach Detector."

## 🛠️ Implementation Blueprint (Pseudo-Code)

1. **Storage (Database):**
   [StudentId] | [RefreshTokenHash] | [ExpiresAt] | [RevokedAt]

2. **Generate Token:**
   - Use `RandomNumberGenerator` to create 64 bytes.
   - Convert to `Base64String`.

3. **Verify & Rotate:**
   - `BCrypt.Verify(incomingToken, storedHash)`
   - If OK -> `Update Student Set RevokedAt = Now`
   - Generate new pair.

## ✅ Summary for Beginners

- **Access Token:** The "Passport" (Show it everywhere, expires soon).
- **Refresh Token:** The "Birth Certificate" (Keep it hidden, use it only to get a new Passport).
- **Revoke:** To "Cancel" the birth certificate so no more passports can be issued.
- **Rotation:** Getting a new birth certificate every time you get a new passport.
